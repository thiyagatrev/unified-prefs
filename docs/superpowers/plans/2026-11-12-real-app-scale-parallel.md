# Real-App Scale: Parallel Plan With Contracts

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to run this plan. Each work package (WP) is one agent in its own git worktree. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Measure the UnifiedPrefs design with 1000 preferences of every type, in a typical (~330 KB) and a heavy (~3.1 MB) profile, against the old stores on the same data, on both platforms.

**Architecture:**
- A Python generator writes the 1000 keys into the Kotlin registry, plus the old-store files for each profile.
- `:storage` gains four value types, a save counter, a checksum and a benchmark routine.
- The iOS migration walks the registry instead of three hand-written keys.
- Both apps get a benchmark launch mode.
- A script seeds the before-state build, upgrades it and collects the numbers.

**Tech Stack:** Kotlin Multiplatform, Jetpack DataStore 1.3.0, Python 3 standard library only (`plistlib`, `struct`, `random`), bash, `adb`, `xcrun simctl`.

**Spec:** `docs/superpowers/specs/2026-11-12-real-app-scale-design.md`. Read it before your package.

**Base:** branch `poc` at commit `210b356` (or later). The earlier plan `2026-11-12-unified-prefs-poc-parallel.md` describes the existing code; its contracts C1–C11 still hold unless changed below.

## How this plan is meant to be run

```
Wave 0  WP-0  contracts as stubs, risky facts proven          (main session)
Wave 1  WP-1  generator (Python)          ┐
        WP-2  repository types + counter  │ parallel, max 3 Gradle
        WP-3  checksum (pure function)    │ packages at once; WP-1
        WP-4  iOS migration + watchers    ┘ runs no Gradle
Wave 2  WP-5  bench routine + Android app ┐ parallel
        WP-6  iOS app bench + baseline    ┘
Wave 3  WP-7  bench.sh, 4 runs, FINDINGS  (main session)
```

- **Wave 0** settles every build question and proves the two risky facts: that a 1000-key Kotlin object compiles on every target, and how to seed the iOS old store.
- **Waves 1 and 2** are written for Haiku-class models. Each package has exclusive files, fixed signatures, named tests with their assertions, and exact commands.
- **Wave 3** is interactive device work and analysis, done by the main session.

## Global constraints

- Everything in the earlier plan's Global constraints still holds: package names, versions, one DataStore per process, legacy file `app_prefs`, DataStore file `app.preferences_pb`, emulator `Pixel_5_API_35`, simulator `iPhone 17`.
- **1000 generated keys:**

  | Type | Count |
  |---|---|
  | Boolean | 350 |
  | Int | 200 |
  | Long | 120 |
  | Float | 80 |
  | Double | 40 |
  | String, short | 150 |
  | String, medium | 30 |
  | String, large | 10 |
  | String set | 20 |

- **Profiles:** `typical` and `heavy`. Only the 10 large strings differ: 10–40 KB in typical, 200–400 KB in heavy.
- **Double keys** appear in the iOS old store only. `SharedPreferences` has no Double type.
- **No new dependencies** in Gradle, Swift Package Manager or Python.
- **Normal launches are unchanged.** Without a bench flag, both apps behave exactly as at `210b356`. The existing upgrade, fresh-install and sync checks must still pass.
- **Generated files** carry the header `// GENERATED by tools/genprefs.py — do not edit.` and are committed.

## Review Focus

1. **A string with XML or plist specials, newlines or emoji** must survive the old store, the migration and the checksum byte for byte (WP-1 self-check; WP-4 test `migratesUnicodeAndEscapes`).
2. **A Float written to the XML as text** must parse back to the identical 32-bit value; a Float in the plist is stored as a double (WP-1 self-check `floatsRoundTrip`).
3. **An iOS number stored as the wrong NSNumber kind**, such as a real in an Int key, must migrate by the registry's type and not crash (WP-4 test `readsNumberByRegistryType`).
4. **Benchmark writes must not change the checksum.** The benchmark writes only `PrefKeys.benchInt` and `PrefKeys.benchText`, never a generated key (WP-5 test `measureLeavesGeneratedValuesUntouched`).
5. **A 1000-key object** must not exceed the JVM 64 KB static-initialiser limit (proven in WP-0 step 3; the fallback is defined there).

### R2. Generated keys, grouped by feature — PLACEHOLDER in Wave 0, REAL from WP-1

Keys are grouped the way a real app's features would own them, one `object` per feature, all in
`:storage`. Constructors stay `internal`, so no other module can declare a key. Callers use either
`repo.getX(SettingsKeys.someKey)` or a getter/setter facade such as `LegacyPrefs`. Both go through
the same repository.

Files, all in package `com.example.unifiedprefs.storage`:
- `storage/src/commonMain/kotlin/com/example/unifiedprefs/storage/keys/<Group>.kt`, one per group.
- `storage/src/commonMain/kotlin/com/example/unifiedprefs/storage/GeneratedKeys.kt`, the combined list.

```kotlin
object SettingsKeys {                 // likewise OnboardingKeys, ProfileKeys, SyncKeys, CacheKeys,
    val feature_flag_0000 = BoolKey("feature_flag_0000", false)   // NotificationKeys, PaymentKeys,
    // ... this group's keys, in generator order                  // AnalyticsKeys
    val all: List<PrefKey> = listOf(...)
}
object GeneratedKeys {
    val all: List<PrefKey> = SettingsKeys.all + OnboardingKeys.all + ProfileKeys.all + SyncKeys.all +
        CacheKeys.all + NotificationKeys.all + PaymentKeys.all + AnalyticsKeys.all
}
```

- **Group assignment:** the key with index `i` within its type goes to group `i % 8`, in the order
  Settings, Onboarding, Profile, Sync, Cache, Notification, Payment, Analytics. Every group then
  holds a mix of types, about 125 keys each.

- **Names by type** (`NNNN` is a zero-padded index within its type):

  | Type | Name pattern |
  |---|---|
  | Bool | `feature_flag_NNNN` |
  | Int | `counter_NNNN` |
  | Long | `last_sync_ts_NNNN` |
  | Float | `ratio_NNNN` |
  | Double | `geo_coord_NNNN` |
  | short String | `label_NNNN` |
  | medium String | `token_NNNN` |
  | large String | `cached_response_NNNN` |
  | Set | `tag_set_NNNN` |

- **Defaults:** `false`, `0`, `0L`, `0f`, `0.0`, `""`, `emptySet()`.
- **Stored names** are the names above, unchanged by grouping, so the old stores and the checksum do not depend on the groups.
- **Wave 0 placeholder:** `object GeneratedKeys { val all: List<PrefKey> = emptyList() }`, with no group files. WP-1 writes the group files and replaces `GeneratedKeys.kt`.

### R4. Checksum — `storage/src/commonMain/.../PrefsChecksum.kt` — STUB in Wave 0, REAL from WP-3

```kotlin
/** 16 lowercase hex chars. */
fun prefsChecksum(keys: List<PrefKey>, valueOf: (PrefKey) -> Any): String
fun PrefsRepository.checksum(keys: List<PrefKey> = GeneratedKeys.all): String = prefsChecksum(keys, ::valueOf)
```

**Algorithm.** 64-bit FNV-1a: offset basis `0xcbf29ce484222325`, prime `0x100000001b3`.
- Keys are sorted by `name`; all names are ASCII.
- For each key, the hash takes, in order: the name's UTF-8 bytes, `0x00`, a type tag byte, then the value.

| Type | Tag | Value bytes |
|---|---|---|
| Bool | 1 | one byte, 0 or 1 |
| Int | 2 | 4 bytes, big-endian |
| Long | 3 | 8 bytes, big-endian |
| Float | 4 | raw IEEE bits, 4 bytes, big-endian |
| Double | 5 | raw IEEE bits, 8 bytes, big-endian |
| String | 6 | 4-byte big-endian length of the UTF-8 bytes, then the bytes |
| Set | 7 | 4-byte big-endian element count, then each element sorted, as its UTF-8 bytes followed by `0x00`; set elements are ASCII |

**Test vector** (Python reference value, fixed):

| Key | Value |
|---|---|
| `tv_bool` | `true` |
| `tv_double` | `-0.1` |
| `tv_float` | `1.5f` |
| `tv_int` | `-2147483648` |
| `tv_long` | `1731400000000` |
| `tv_set` | `{"b","a","c"}` |
| `tv_str` | `"நன்றி 🙏 <a&b>"` |
| `tv_unset` | `StringKey` with default `"dflt"`, value `"dflt"` |

- The checksum of this vector is `226e901c9354c740`.
- An empty key list gives `cbf29ce484222325`.

Ruling recorded against the spec: strings carry a length prefix, so the encoding is unambiguous. The spec said only "UTF-8".

### R5. Benchmark — `storage/src/commonMain/.../PrefsBench.kt` — STUB in Wave 0, REAL from WP-5

```kotlin
class BenchResult(val checksum: String, val saveMs: Double, val burstMs: Double, val burstSaves: Int)
object PrefsBench {
    /** Runs on the calling thread; blocks. Writes only PrefKeys.benchInt and PrefKeys.benchText. */
    fun measure(repo: PrefsRepository): BenchResult
    fun datastoreLine(loadMs: Double, keysMs: Double, r: BenchResult): String
    fun baselineLine(loadMs: Double, saveMs: Double): String
}
```

`measure` runs these steps in order:
1. `checksum = repo.checksum()`.
2. `saveMs`: the time to `putInt(benchInt, getInt(benchInt) + 1)` plus a blocking `flush()`.
3. `burstMs`: the time to `putString(benchText, "bench-$i")` for `i` in `0..99`, plus a blocking `flush()`.
4. `burstSaves`: the change in `saveCount` across step 3.

Time with `kotlin.time.TimeSource.Monotonic`. Format each millisecond value with one decimal place (`12.0`, `3.4`).

**Exact lines:**

```
UNIFIEDPREFS_BENCH mode=datastore load_ms=<d> keys_ms=<d> checksum=<hex16> save_ms=<d> burst_ms=<d> burst_saves=<n>
UNIFIEDPREFS_BENCH mode=baseline load_ms=<d> save_ms=<d>
```

### R6. Bench launch mode (apps)

| | Android (`PocApp.onCreate`) | iOS (`PocApp.init`) |
|---|---|---|
| Selector | file `filesDir/bench_mode` containing `datastore` or `baseline`; absent → normal | launch arguments `--bench datastore` / `--bench baseline` |
| `datastore` | time `PrefKeys.allKeys.size` → `keysMs`; then time `prefsRepository(this)` → `loadMs`; `PrefsBench.measure`; log the `datastoreLine` with tag `UnifiedPrefs` | time `PrefKeys.shared.allKeys.count` → `keysMs`; then time `IosStorage.shared.repo` → `loadMs`; `PrefsBench.shared.measure`; print the `datastoreLine` |
| `baseline` | time `getSharedPreferences("baseline_prefs", MODE_PRIVATE).all` → `loadMs`; time `edit().putInt("bench_int", n + 1).commit()` → `saveMs`; log the `baselineLine` | time `UserDefaults(suiteName: "baseline")!.dictionaryRepresentation()` → `loadMs`; time `set(_:forKey: "bench_int")` + `synchronize()` → `saveMs`; print the `baselineLine` |
| After | continue the normal start (`UNIFIEDPREFS_LOAD`, then `UNIFIEDPREFS_STATE`) | same |

The bench step runs **before** any other storage access in the process.

Key setup is timed first and on its own (`keys_ms`). Otherwise it lands inside `load_ms` on iOS, whose migration walks every key, but not on Android, whose migration never touches the registry. That would skew the comparison.

Ruling: the iOS baseline `saveMs` times the call plus `synchronize()`. `UserDefaults` writes to disk in another process, so it is not a time-until-on-disk. FINDINGS must say so.

### R7. Generator — `tools/genprefs.py` — REAL from WP-1

```
python3 -I tools/genprefs.py --kotlin storage/src/commonMain/kotlin/com/example/unifiedprefs/storage
python3 -I tools/genprefs.py --profile <typical|heavy> --out build/genprefs
python3 -I tools/genprefs.py --self-check
```

`--profile` writes into `build/genprefs/<profile>/`:

| File | Content |
|---|---|
| `app_prefs.xml` | Android old store: 960 generated keys (no Doubles) plus `dark_mode=true`, `launch_count=3`, `user_name=Asha` |
| `legacy.plist` | iOS old store, binary plist: all 1000 keys plus `isDarkMode=true`, `launchCount=3`, `userName=Asha` |
| `expected-android.txt`, `expected-ios.txt` | the R4 checksum over `GeneratedKeys.all`, with Double keys at their defaults for Android |
| `sizes.txt` | the total UTF-8 bytes of all values |

Sizes must fall within typical 250–450 KB and heavy 2.8–3.6 MB.

- **Seed:** `random.Random(20261112)`. Both profiles draw the same values for every key except the large strings, which use their own child RNG per profile.
- **Android XML format:** the one `SharedPreferences` writes:
  - header `<?xml version='1.0' encoding='utf-8' standalone='yes' ?>` and root `<map>`;
  - elements `<boolean name= value= />`, `<int …/>`, `<long …/>`, `<float …/>`, `<string name=…>text</string>`, and `<set name=…><string>…</string></set>`;
  - text escaped with `xml.sax.saxutils.escape` plus `"` → `&quot;` in attributes.
- **Floats:** generate a value, round it to float32 with `struct.unpack('>f', struct.pack('>f', x))[0]`, and write `repr()` of that value.
